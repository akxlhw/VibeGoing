# VibeGoing 版本发布计划

> 版本策略、发布序列与发布流程。故事明细见 [BACKLOG.md](BACKLOG.md)，里程碑背景见 [PLAN.md](../../PLAN.md)。
> 状态：v1.0（2026-09-06 制定）。日期为目标值（按单人全职节奏估算），兼职节奏约 ×2。

## 1. 版本策略（语义化版本）

- **0.x 阶段**（M0–M4）：`0.<里程碑序号>.0`，次版本号与里程碑一一对应；API 与数据格式允许不兼容变更（CHANGELOG 中显著标注）
- **1.0.0**（M5 后）：首个稳定版——PLAN.md 全部里程碑验收通过、格式与 API 进入兼容性承诺
- **补丁版** `0.x.N`：仅缺陷修复（VG-9xx），不引入新故事内容
- **预发布标签**：里程碑延期风险高时先出 `rc`（如 `0.4.0rc1`），最多两轮 rc 后必须转正或砍范围
- 版本号出现位置保持一致：`pyproject.toml`、`vibegoing/__init__.py::__version__`、git tag、GitHub Release

## 3. 发布流程（每个版本的 checklist）

1. **范围冻结**：里程碑全部故事 DoD 完成，`待验收` 清空（退回项明确延后到下版本）
2. **PO 验收**：对照 PLAN.md 该里程碑验收标准逐条演示，PO 确认
3. **版本一致性**：`pyproject.toml` 与 `__version__` 同步 bump；CI 绿
4. **CHANGELOG 定稿**：`[Unreleased]` → `[vx.y.z] - 日期`，新开空 `[Unreleased]`
5. **打 tag**：annotated tag `vx.y.z` 于 main
6. **GitHub Release**：Notes 取自 CHANGELOG 对应段落；附交付物（安装包自 v0.5 起）
7. **回填档案**：冲刺文档记录发布结论；BACKLOG 状态批量置"完成"
8. **下版本预热**：新里程碑的 Sprint 计划就绪

## 4. 热修复流程（patch）

1. 从 tag `vx.y.z` 拉 `hotfix/vx.y.z` 分支
2. 修复 + 测试 + CHANGELOG 增补 `[vx.y.z+1]`
3. CI 绿 → 合回 main **并同时打** `vx.y.z+1` tag（保持 main 包含全部修复）
4. 仅 P0/P1 缺陷走此通道；其余缺陷进 BACKLOG 随常规版本发布

S1(09-07) S2(09-14) │ S3(09-21) S4(09-28) │ S5(10-05) S6(10-12) │ S7(10-19) S8(10-26) │ S9(11-02)

- 每个版本出口 = 对应冲刺的周五评审通过即发布（当日完成 §3 checklist）
- 里程碑内故事若未完成：优先砍范围保版本节奏（进下版本），不做无声延期——砍范围需 PO 确认并更新 PLAN.md
